## 1. 项目概述

### 1.1 项目定位

AI 狼人杀是一个支持**单人/多人参与、剩余位置由 AI 自动补齐**的在线狼人杀游戏。核心卖点：**随时开玩，无需凑人**。

### 1.2 目标用户

- 想练狼人杀但凑不齐人的玩家
- 朋友小圈子想快速开一局（2-4 真人 + AI 补齐）
- 对 AI 社交推理能力感兴趣的技术用户

### 1.3 平台

- **首期**：Web 端（React）
- **后期**：移动端 App（可复用后端）

## 2. 游戏规则

### 2.1 游戏流程

```
游戏开始 → 分配身份
         → 夜晚阶段
             狼人刀人（需协商）→ 预言家验人 → 女巫用药/毒 → 守卫守人
         → 白天阶段
             公布死讯 → 轮流发言 → 投票放逐
         → 重复日夜循环直到胜负判定
```

### 2.2 角色定义

| 角色   | 阵营  | 能力             | 说明                           |
| ---- | --- | -------------- | ---------------------------- |
| 狼人   | 狼人  | 每晚可刀一人         | 狼人间互相认识，夜晚需协商刀人目标            |
| 村民   | 好人  | 无特殊能力          | 通过发言和投票找出狼人                  |
| ⭐预言家 | 好人  | 每晚可查验一人身份      | 知道所查人是好人还是狼人                 |
| ⭐女巫  | 好人  | 拥有一瓶解药+一瓶毒药    | 解药可救活夜间被杀者；毒药可毒杀一人。两瓶药各只能用一次 |
| 守卫   | 好人  | 每晚可守护一人        | 被守护的人当晚不会被刀。不可连续两晚守护同一人      |
| 猎人   | 好人  | 被放逐/刀杀时可开枪带走一人 | 被毒杀时不能开枪                     |

> ⭐ = Phase 1 必实现角色。守卫、猎人 Phase 3 加入。

### 2.2.1 局后 MVP/SVP 评选

每局结束后自动评选：

- **MVP**（胜方最有价值玩家）：对胜利贡献最大的玩家
- **SVP**（败方最有价值玩家）：败方中表现最好的玩家

**评选机制**（Phase 1 用方案 A，后续可切换）：

| 方案 | 机制 | 优点 | 缺点 |
|------|------|------|------|
| **A. AI 投票制（首期）** | 存活 AI 玩家投票选出 MVP/SVP，附带理由 | 实现简单，符合"玩家互评"直觉 | AI 可能投票不客观 |
| **B. 积分制** | 关键行为自动计分（预言家验到狼 +3，狼活到最后 +5，女巫毒中狼 +4…），最高分当选 | 客观可量化 | 难以覆盖"带节奏""挡刀"等隐性贡献 |
| **C. 混合制** | 积分制缩小候选范围（Top 3），再由 AI 投票选出 | 兼顾客观和主观 | 实现复杂度高 |

**MVP/SVP 的作用**：
- 给玩家成就感（尤其单人局）
- 调试 AI 行为 —— 查看 MVP 的发言/决策记录分析为什么强
- 未来可做排行榜

### 2.3 胜负条件

| 阵营 | 胜利条件 |
|------|----------|
| 好人阵营 | 放逐所有狼人 |
| 狼人阵营 | 存活狼人数 ≥ 存活好人数（屠边） |

### 2.4 游戏配置

**首期 MVP 配置（6人局）：**

| 角色 | 数量 |
|------|------|
| 狼人 | 2 |
| 村民 | 2 |
| 预言家 | 1 |
| 女巫 | 1 |
| **总计** | **6** |

真人数量：1~6 人可配。剩余位置 AI 补齐。**最少支持 1 真人 + 5 AI。**

**二期扩展配置：**
- 9人局：3狼 + 3民 + 预言家 + 女巫 + 猎人
- 12人局：4狼 + 4民 + 预言家 + 女巫 + 猎人 + 守卫

|------|--------|------|
| 创建房间 | P0 | 房主选择游戏配置（人数、角色模版）、设置真人数量 |
| 加入房间 | P0 | 通过房间号加入 |
| 房间等待 | P0 | 展示当前玩家列表、AI 占位数量，房主可踢人/开始游戏 |

### 3.2 游戏核心

| 功能 | 优先级 | 描述 |
|------|--------|------|
| 身份分配 | P0 | 开局随机分配身份，狼人互相可见 |
| 夜晚阶段 | P0 | 按顺序执行各角色行动，有操作时限 |
| 白天-公布死讯 | P0 | 播报昨晚死亡情况（谁死了、是否平安夜） |
| 白天-发言阶段 | P0 | 按顺序发言，每人有时间限制 |
| 白天-投票阶段 | P0 | 存活玩家暗投、同时开票，票多者出局（不可跟票） |
| 狼人自爆 | P1 | 白天任一狼人可主动亮身份，立即结束发言，直接进入天黑 |
| 猎人开枪 | P1 | 猎人被票出/被刀时可选择开枪带走一人（被毒不能开枪） |
| 遗言 | P0 | 首夜死者、首轮被票者、之后所有被刀者（除最后一轮）均可留遗言 |
| 平票处理 | P0 | 平票时平票者补充发言 → 二次投票 → 仍平票则无人出局 |
| 平安夜 | P0 | 无人死亡时公告"昨晚是平安夜" |
| 同守同救 | P1 | 守卫守护+女巫解救同一人时，该玩家仍死亡（规则冲突） |
| 女巫不可自救 | P0 | 女巫被刀时不可用解药自救 |
| 胜负判定 | P0 | 每有人出局后立即检查胜利条件 |
| 警长系统 | P2 | 12人局首日警长竞选、死后移交警徽、警长投票权+0.5 |
| 游戏回放 | P2 | 结束后可查看完整发言记录和身份 |

### 3.3 AI 系统（详见第 4 节）

| 功能 | 优先级 | 描述 |
|------|--------|------|
| AI 夜晚决策 | P0 | AI 根据身份做出夜晚行动；狼人间异步协商 |
| AI 白天发言 | P0 | AI 生成自然语言发言（包含逻辑分析/心路历程/谎言/情绪） |
| AI 投票 | P0 | AI 根据局势决定投票目标 |
| AI 持续思考 | P0 | AI 在发言间隙持续更新内部判断，非一次性完成 |
| AI 角色扮演 | P1 | 每个 AI 有独立 persona 和玩法风格 |
| AI 一致性 | P1 | AI 自维护记忆，不出现逻辑矛盾 |
| AI 策略系统 | P1 | 预设策略知识库 + 运行时动态调整 |

### 3.4 语音与输入

| 功能 | 优先级 | 描述 |
|------|--------|------|
| 文字输入 | P0 | 玩家通过聊天框输入发言内容 |
| 玩家语音输入 | P1 | 玩家可选语音输入，前端录音 → 后端语音识别（STT）→ 转为文字发言 |
| AI 发言 TTS | P1 | AI 发言文字转语音，前端自动朗读 |
| 系统播报 TTS | P2 | 死讯通知、阶段切换等用语音播报 |

> **输入分离设计**：玩家的语音和文字输入走同一发言管道——语音识别后以文本形式进入聊天区，AI 和人类看到的内容一致（都是文本）。TTS 仅用于 AI 发言朗读给人类听。

| 聊天面板 | P0 | 文字聊天区，区分玩家/AI/系统消息，支持语音输入按钮 |
| 投票面板 | P0 | 显示候选人，点击投票 |

| 游戏日志 | P1 | 可查看历史消息和行动记录 |

### 3.6 容错与异常处理

| 异常场景 | 触发条件 | 处理方式 |
|----------|----------|----------|
| LLM API 超时/失败 | AI 调用无响应 | ① 重试 2 次（3s 间隔）；② 仍失败 → 切换备用 AI 模型；③ 备用也失败 → 规则引擎兜底（随机/默认行为） |
| 真人玩家断线 | WebSocket 断开 | ① 240s 内重连 → 回到原位置 + **补发断线期间所有消息**；② 超时 → AI 接管 |
| 断线重连-数据补发 | 玩家重连成功 | 服务端推送：① 当前状态快照（阶段、存活名单、投票状态）；② 断线期间错过的聊天记录 + 系统事件增量列表；③ 若正在发言中 → 补发已生成的发言文本。前端恢复完整 UI 状态 |
| 狼人协商 AI 无响应 | 某狼人 API 失败 | 其他狼人多数决，无响应者视为弃权 |
| AI 发言生成超时 | 超过 60s 未生成 | 使用预置模板发言兜底（"我还没想清楚，先过"） |
| TTS 服务不可用 | Edge TTS 返回错误 | AI 发言仍以文字显示，TTS 静默降级，不影响游戏 |
| 房间不存在 | 玩家输入无效房间号 | 前端提示"房间不存在"，引导创建新房间 |
| 全员 AI 某阶段卡死 | 所有 AI 同时失败 | 系统自动跳过该阶段，记录异常日志 |

> **备用 AI 模型**：主模型配置 + 备用模型配置。如主用 GPT-4o，备用用 DeepSeek。

## 4. AI 系统设计

### 4.1 核心设计原则

1. **AI 读文本是瞬间的**。TTS 仅服务于人类耳朵，不阻塞 AI 思考流程。
2. **思考是持续的过程**。AI 每听完一个发言就更新内部判断，而非在发言前一次性生成。
3. **历史记忆由 AI 自己维护**。不做后端统一摘要——每个 AI 自行决定什么信息重要。
4. **策略是动态的**。预设策略知识库提供方向，但 AI 根据局势实时评估是否调整。

### 4.2 AI 上下文结构

每次调用 LLM 时，注入以下完整上下文。**上下文必须经过 Projection 过滤**——AI 只能看到 `buildPlayerView(state, aiPlayerId)` 的结果，防止"作弊"。

```
┌──────────────────────────────────┐
│ System Prompt                    │  游戏规则 + 角色能力 + Persona
├──────────────────────────────────┤
│ 身份信息 + 策略知识               │  真实身份、伪装身份、角色策略库
├──────────────────────────────────┤
│ 隐藏信息（仅本AI可见）             │  狼同伴是谁、药水状态、查验结果等
├──────────────────────────────────┤
│ 公开局势                         │  存活/死亡名单、当前第几天、第几轮发言
├──────────────────────────────────┤
│ 本轮完整发言历史                   │  1号说了什么、2号说了什么...（原文，非摘要）
├──────────────────────────────────┤
│ 往轮摘要（AI自维护）               │  "第1天我踩了5号，第2天..."（AI自己写的摘要）
├──────────────────────────────────┤
│ AI内心记忆（AI自维护）             │  "我的当前策略是...""我撒过的谎：..."
│                                   │  "我对各玩家的当前判断：1号像民、3号可疑..."
├──────────────────────────────────┤
│ 当前任务                         │  生成发言 / 决定投票 / 夜晚行动 / 策略复核
└──────────────────────────────────┘
```

**关键设计**：
- 往轮发言用**摘要**而非原文——完整发言历史越来越长会超出 token 限制
- 摘要由 **AI 自己生成**，后端不做统一摘要。因为不同身份关注的信息不同（狼人和村民认为"重要"的东西不一样）
- 隐藏信息包括 AI 需要伪装的角色（如狼人伪装成村民/预言家）

### 4.3 AI 持续思考流程

AI 不是在发言前一次性完成思考，而是在整个白天阶段持续更新内部状态。

```
T0  开局：确定初始策略，建立初始判断
     ↓
T1  听完1号发言：AI立即读取文本 → 更新对1号的判断 → 调整内部推理
     ↓
T2  听完2号发言：AI立即读取文本 → 更新对2号的判断 → 重新评估局势
     ↓
...  （每个发言间隔，AI都在思考）
     ↓
轮到AI自己发言：基于累积的判断生成发言
     ↓
T_n 发言继续，AI继续听取后续发言 → 持续更新判断
     ↓
投票：基于最终判断投票
```

**时间利用**：AI 在发言间隙的思考是并行的。当 TTS 在播放发言给人类听时，AI 已经读完文本并完成了判断更新。

### 4.4 AI 三种决策场景

#### A. 夜晚行动

##### 狼人：异步协商制

狼人之间需要协商刀人目标，但不能拖慢节奏。采用**两轮异步协商**：

```
夜晚开始
  │
  ├─ 第1轮：提案（所有狼人并发）
  │   每个狼人独立调用 LLM，给出：
  │   - 建议刀谁
  │   - 理由
  │   - 携带隐藏信息（狼同伴、已知查验等）
  │   耗时：~3s（并行）
  │
  ├─ 引擎收集提案，判断是否一致
  │   ├─ 所有狼人一致 → 直接执行，跳过第2轮
  │   └─ 存在分歧 → 进入第2轮
  │
  ├─ 第2轮：决议（所有狼人并发）
  │   把第1轮所有狼人的提案传给每个狼人：
  │   "3号说刀5号因为...，7号说刀2号因为...，你的最终决定？"
  │   耗时：~2s（并行）
  │
  └─ 多数决 → 执行
```

> 狼人间不需要隐晦聊天频道——采用共享提案+投票制，快速高效。

##### 其他角色：独立决策（并发）

预言家、女巫、守卫（Phase 3）的夜间行动各自独立，**无协商需求**，全并发执行。

**预言家查验**：通过直接消息通知结果，不经过 LLM。

```
流程：
  预言家选择查验目标 → 引擎查询该目标身份 → 直接返回"好人/狼人"
  （无需 LLM 参与——查验是确定性操作）
```

**女巫用药**：获取死者信息通过直接消息，决策是否用药走 LLM。

```
流程：
  引擎推送死者信息（直接消息："昨晚 X 号被杀"）→ 女巫 LLM 决策是否用药
  （信息获取不走 LLM，决策走 LLM）
```

| 角色 | 信息获取方式 | 决策方式 | 耗时 |
|------|-------------|----------|------|
| 预言家 | 引擎直接返回查验结果 | 选择目标走 LLM | ~5s |
| 女巫 | 引擎直接推送死者信息 | 是否用药走 LLM | ~5s |
| 守卫 | 引擎直接告知守护历史 | 选择目标走 LLM | ~5s |

> 原则：**确定性信息查询**（查验结果、死者身份、药水状态）直接由引擎返回，不浪费 LLM token。**策略决策**（选谁、用不用药）才调用 LLM。

#### B. 白天发言

**发言要求**：150-400 字，包含逻辑分析、心路历程、对前置发言的拆解、结合身份立场的倾向性判断。不是简单表态。

**发言生成 Prompt 核心要素**：

```
你的身份和目标：
- 真实身份 + 伪装身份
- 当前策略和进展
- 本轮发言的核心目的

前置发言分析：
- 1号说了："..." → 你的判断：他说的是真是假？为什么？
- 2号说了："..." → 你的判断：逻辑漏洞在哪里？
- ...

请生成发言，要求：
- 包含逻辑推理和心路历程
- 点评关键发言者
- 给出你的倾向性
- 符合你的伪装身份
- 不暴露你的隐藏信息
```

**时间模型**：

```
AI处理视角：
  发言1生成(3-5s) → [所有AI瞬间读取，更新判断]
  → 发言2生成(3-5s) → [所有AI瞬间读取，更新判断]
  → ... → 发言N生成(3-5s)

人类感知视角（同时进行）：
  → 发言1 TTS播放(15-30s) → 发言2 TTS播放(15-30s) → ...
```

**总时间**（10人局）：AI 处理 30-50s，TTS 播放 2.5-5min。AI 思考完全掩藏在 TTS 播放窗口内。

**玩家发言**：真人玩家通过文字输入或语音输入（STT 转文字）发言，同样顺序参与。AI 将玩家发言文本一并读取和分析。

**流式发言推送**：AI 发言生成时，服务端以 SSE 流式推送分块到前端：

```
Socket 事件：
  game:speech_chunk  { playerId, chunk, isLast }
  game:speech_end    { playerId, fullText }

前端行为：
  收到 chunk → 追加到发言区域（打字机效果）
  收到 speech_end → 触发 TTS 朗读（完整文本）
```

AI 的 Think 层在生成首个 chunk 前完成，Plan 层与 Speak 层可合并为一次 LLM 调用（`stream: true`），减少延迟。

#### C. 投票

采用**暗投 + 同时开票**机制，玩家不可跟票。

```
流程：
  所有存活玩家（含 AI）并发提交投票目标
  ↓
  收集完毕 → 同时公布所有投票结果
  ↓
  票多者出局（不可在开票后改票）

输入：
- 本轮所有发言（完整原文）
- 当前局势
- 自己的阵营目标和隐藏信息

输出：投票目标或弃票

耗时：~2s（AI并行），+ 真人操作时限15s
```

**暗投+同时开票的好处**：
- 无人可以"看情况跟票"，保证公平
- 真人玩家和 AI 玩家投票体验一致
- 前端实现：投票阶段显示候选人面板 → 每人点击选择 → 等待所有人完成 → 统一展示结果动画

### 4.5 策略系统

策略知识依附于角色身份，与身份信息写在一起。AI 在获得身份的同时获得该身份的策略知识库。

#### 静态策略知识库

策略知识库是结构化内容，每条策略包含：**执行计划、触发条件、退出条件、风险等级、范例话术、反策略**。AI 开局时根据身份+局势从策略库中选择初始策略。

##### 狼人策略

**1. 悍跳预言家**

| 维度 | 内容 |
|------|------|
| 核心思路 | 伪装成预言家，报假查验引导票向，与真预言家争夺话语权 |
| 执行步骤 | ① 首轮听发言，判断场上是否有"像预言家"的人；② 白天抢先跳身份，报出一个假查验（通常给好人发金水或给同伴发查杀）；③ 每轮持续更新假查验信息，保持前后一致；④ 与真预言家争夺警长/票权 |
| 触发条件 | 首轮或次轮；场上气氛适合起跳（自己发言位置靠前更优）；有同伴可以打配合 |
| 退出条件 | 被验出矛盾且无法自圆其说 → 考虑自爆；真预言家发言明显强于自己 → 转为煽动/倒钩 |
| 风险等级 | ★★★★☆ 高 |
| 范例话术 | "昨天晚上我验了3号，是金水。3号可以带队。后面有对跳的直接标狼打。" |
| 反策略 | 真预言家应明确指认悍跳狼的逻辑漏洞；女巫可通过银水信息反证 |

**2. 倒钩狼**

| 维度 | 内容 |
|------|------|
| 核心思路 | 深度卧底好人阵营，全程站边真预言家，获取信任后暗中破坏 |
| 执行步骤 | ① 首轮低调发言，不引起注意；② 主动站边真预言家，积极帮好人分析；③ 投票跟随好人阵营，确保自己不被怀疑；④ 后期局势明朗时，利用信任关系误导关键投票 |
| 触发条件 | 已有明确的真假预言家对立局面；自身发言能力不足以悍跳 |
| 退出条件 | 同伴被真预言家验出且可能被推出 → 考虑悍跳/自爆掩护；自己伪装被识破 → 转为煽动 |
| 风险等级 | ★★☆☆☆ 低 |
| 范例话术 | "我听完两轮觉得5号预言家面更大。2号悍跳的发言有逻辑漏洞——他说验了4号，但4号刚才发言明显是狼人视角。" |
| 反策略 | 预言家查验倒钩狼时会被揭穿；女巫毒药可定向清除"表现太好"的人 |

**3. 自刀**

| 维度 | 内容 |
|------|------|
| 核心思路 | 狼人刀自己同伴（或自己被刀），骗取女巫解药和银水身份，获得铁好人身份 |
| 执行步骤 | ① 夜晚协商时提议自刀，选择场上面相好的狼人；② 天亮后等待公布死讯——平安夜则说明女巫救了；③ 被救者以银水身份发言，占据道德高地；④ 利用铁好人身份引导票向 |
| 触发条件 | 女巫解药尚未使用（首夜最佳）；被自刀者发言能力强；局势允许减员一只狼 |
| 退出条件 | 女巫首夜不救 → 自刀狼死亡，策略失败；女巫公开银水信息 → 需维持伪装 |
| 风险等级 | ★★★★★ 极高 |
| 范例话术 | "我是银水，女巫可以出来认一下。昨晚我差点死了，说明狼人盯上我了，好人跟我走。" |
| 反策略 | 女巫首夜不救是标准打法；好人应警惕"银水不一定铁好" |

**4. 煽动狼**

| 维度 | 内容 |
|------|------|
| 核心思路 | 不跳任何身份，纯靠话术带节奏，通过质疑、暗示、挑拨离间制造混乱 |
| 执行步骤 | ① 每轮发言都积极踩人，但不固定目标；② 制造"谁和谁是同伴"的暗示；③ 利用发言者的逻辑漏洞无限放大；④ 投票时故意与同伴投不同目标，避免暴露连狼 |
| 触发条件 | 场上局势混乱，多方互踩；自己不擅长跳身份 |
| 退出条件 | 被多人集中怀疑 → 减少发言频率转为深水；同伴需要支援 → 转为阴阳倒钩 |
| 风险等级 | ★★★☆☆ 中 |
| 范例话术 | "大家有没有发现3号和5号的发言高度一致？每次5号说什么3号就附议。这很不正常，要么是共群，要么是5号在带3号的节奏。" |
| 反策略 | 好人应集中分析煽动狼的发言，找出"踩人造谣"的规律；预言家优先验

**5. 阴阳倒钩**

| 维度 | 内容 |
|------|------|
| 核心思路 | 表面踩同伴，实际在保同伴——通过明踩暗保的方式掩护狼队友 |
| 执行步骤 | ① 在发言中点名批评某位同伴，但理由牵强；② 让好人觉得"这个人在乱踩，他踩的人反而可能是好人"；③ 投票时不投自己踩的人；④ 如果同伴被推出，自己的嫌疑也洗清了 |
| 触发条件 | 多狼存活（≥3只）；某位同伴面临被怀疑的压力 |
| 退出条件 | 被识破阴阳倒钩 → 转为直接踩人（牺牲同伴）；同伴已被保护成功 → 恢复正常 |
| 风险等级 | ★★★☆☆ 中 |
| 范例话术 | "我觉得6号发言有点问题，他刚才的逻辑链条不完整。不过我建议今天先出4号，4号更像狼。" |
| 反策略 | 好人应关注"踩人但不投票"的行为模式；预言家可验6号验证 |

**6. 隐狼 / 深水狼**

| 维度 | 内容 |
|------|------|
| 核心思路 | 全程极度低调，发言简短划水，不引起任何注意，活到最后收割 |
| 执行步骤 | ① 每轮发言控制在 50-80 字，内容模糊；② 不主动踩人也不站边；③ "我觉得信息还不够，先听听后面的发言"是常用话术；④ 投票随机或随大流 |
| 触发条件 | 任何时候都可执行；适合发言能力弱的 AI |
| 退出条件 | 同伴全部阵亡 → 必须转为主动策略；被预言家怀疑 → 考虑自爆或反踩 |
| 风险等级 | ★☆☆☆☆ 低（风险低但也难有功） |
| 范例话术 | "这一轮发言信息量很大，我需要消化一下。目前我倾向于跟着预言家走，看看后面的发言怎么发展。" |
| 反策略 | 好人应警惕"全程划水"的人——狼人最喜欢低调；预言家可验"不说话的人" |

##### 预言家策略

**1. 首验优先级策略**

| 维度 | 内容 |
|------|------|
| 核心思路 | 选择最优首验目标，最大化查验信息收益 |
| 决策规则 | ① 优先验发言积极者（如果是狼则危害大，如果是好人则能带队）；② 其次验极度沉默者（沉默的可能是狼人）；③ 验高位（发言靠前的人）因为高位发言影响力大；④ 避免验自己能判断的人 |
| 补充 | 第二夜验与首验结果形成关联的人（如首验金水，则验被金水怀疑的人） |

**2. 跳身份时机策略**

| 维度 | 内容 |
|------|------|
| 首轮跳 | 优势：第一时间掌握话语权；劣势：暴露自己给狼人刀 |
| 次轮跳 | 优势：可等悍跳狼先暴露出漏洞；劣势：失去首轮话语权 |
| 隐藏不跳 | 优势：不暴露；劣势：好人失去信息源，狼人更容易控场 |
| 决策条件 | 如果首验是查杀 → 首轮跳；首验是金水 → 可观察一轮再跳；死人信息可能有遗言透露身份 |

**3. 查验结果上报策略**

| 维度 | 内容 |
|------|------|
| 全部真报 | 所有查验结果如实公开，建立可信度 |
| 部分隐藏 | 某些查验结果（如验到守护神职）不公开，保护神职 |
| 关键原则 | 验到狼人必须报；验到金水报不报取决于该金水是否需要保护 |

##### 女巫策略

**1. 解药使用策略**

| 场景 | 决策 | 理由 |
|------|------|------|
| 首夜有人被杀 | 建议救（Phase 1 默认） | 首夜死者信息量小，救活增加好人数量 |
| 第2夜后有人被杀 | 选择性救 | 如果死者是发言好的人/神职面相 → 救；如果是划水民 → 可留药 |
| 自己被杀 | 不可自救 | 规则限制，不可用解药救自己 |

**2. 毒药使用策略**

| 场景 | 决策 |
|------|------|
| 明确识破某狼人 | 直接毒杀（必须在夜间） |
| 某人发言极度可疑 | 结合预言家查验信息，若独立判断确信是狼 → 毒 |
| 局势不明 | 保留毒药，威慑狼人不敢悍跳 |

**3. 银水信息透露策略**

| 方式 | 场景 |
|------|------|
| 不透露 | 绝大多数情况——让狼人不知道银水是谁 |
| 暗示 | 发言中说"我对某号有好感"，帮助银水获得信任 |
| 直接报 | 自己即将被刀/被票时，留遗言公开银水身份 |

##### 村民策略

**1. 推理优先级**

```
关注顺序：
① 发言矛盾点（前后不一致）
② 票型（谁投了谁，是否跟预言家投票）
③ 发言风格一致性（是否突然改变风格）
④ 身份跳出的合理性（多人跳同一身份 → 至少一个是狼）
```

**2. 站边策略**

```
如何判断真假预言家：
① 查验逻辑是否自洽（真预言家不会前后矛盾）
② 发言自然度（悍跳狼发言可能过于"完美"）
③ 被查验者的反应（被发金水的人是否反常地低调？被发查杀的人是否在挣扎时暴露？）
④ 心态（真预言家往往有"追着狼咬"的紧迫感，悍跳狼心态更放松）
```

**3. 表水策略**

| 被怀疑原因 | 应对方式 |
|------------|----------|
| 发言太少 | 主动梳理局势，展示自己的分析过程 |
| 踩了某个人 | 解释踩人逻辑，提供具体论据而非空泛指责 |
| 投票异常 | 解释投票动机，承认"那轮我是错了"比狡辩更好 |

**4. 挡刀策略（高玩向）**

| 维度 | 内容 |
|------|------|
| 核心思路 | 刻意表现出神职面相（谨慎发言、暗示有身份），吸引狼人刀自己，保护真正的神职 |
| 执行条件 | 自己是民且局势进入中后期；至少有1-2个神职身份尚未暴露 |
| 风险 | 做得太过会被好人当狼投出去；做得不够狼人不吃 
#### 运行时动态调整

开局时 AI 从策略库中选定初始策略。每轮发言/投票前，做一次策略复核：

```
策略复核 Prompt：

当前策略：倒钩狼
当前进展：已执行2轮，成功取得部分好人信任
最新局势：4号跳预言家，报了3号（AI自己）金水

策略库中倒钩狼的退出条件：
- 同伴被查验且可能被推出 → 考虑转为悍跳或煽动
- 伪装被识破 → 策略作废，需新策略
- 局势对狼人极度不利 → 考虑自刀博取信任

请判断：继续倒钩 or 切换策略？如果切换，切哪个？原因？
```

**关键**：策略不是死的。听完一个人的发言后，AI 可能决定"我原来的策略不适合了，需要换"。

#### 策略知识库实现方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| System Prompt 嵌入 | 策略直接写在 prompt 中 | 简单可靠 | token 消耗大 |
| RAG 检索 | 策略存向量库，按需检索 | 灵活扩展 | 检索准确性依赖 embedding |
| **混合（推荐）** | 核心高频策略放 prompt + 冷门策略 RAG | 兼顾效率和覆盖 | 实现复杂度中等 |
| 规则引擎 + LLM | 明确条件用规则，模糊判断用 LLM | 可解释性强 | 维护成本高 |

首期 MVP 使用 **System Prompt 嵌入**（策略数量少，token 够用），二期引入 RAG。

### 4.6 AI 自维护记忆

每个 AI 维护一段内部记忆文本，在每轮结束后由 AI 自己更新：

```
内部记忆结构（以狼人AI为例）：

【我的身份】
真实身份：狼人
同伴：6号
伪装身份：村民（倾向于分析型玩法）

【当前策略】
策略：倒钩狼
执行阶段：第2天
伪装要点：发言积极但不过分，适当表达困惑以显得像平民

【我撒过的谎/需要记住的】
- 第1天我说"我觉得1号发言有问题"（其实1号发言没问题，我在引导怀疑）
- 第2天我说"5号像好人"（其实在捧杀）

【我对各玩家的判断】
- 1号：民面相，发言朴素
- 2号：可能是神，发言谨慎
- 4号：跳预言家，暂时判断为真预言家
- 5号：发言有漏洞，可能是民
- 6号：我的同伴，他目前低调中

【本轮计划】
- 继续捧4号预言家，避免引起怀疑
- 暗示2号可能是狼（转移焦点）
- 投票倾向：票2号
```

**记忆更新时机**：每轮发言/投票结束后，AI 追加一句"本轮发生了什么 → 我学到了什么 → 下轮计划"。

### 4.7 Persona 系统（P1）

为每个 AI 生成独特的玩家风格，确保每局体验不同：

| 性格维度 | 范围 | 影响 |
|----------|------|------|
| 攻击性 | 温和 ← → 激进 | 发言措辞、踩人频率 |
| 发言量 | 话少简洁 ← → 长篇大论 | 字数控制 |
| 情绪表现 | 理性冷静 ← → 情绪化 | 感叹号使用、情绪词汇 |
| 策略偏好 | 保守 ← → 冒险 | 对高风险策略（悍跳/自刀）的倾向 |
| 语言风格 | 随意口语 ← → 正式分析 | 用词和句式 |

每局随机生成 persona 组合，让不同 AI 的发言风格有区分度。

### 4.8 一致性与防作弊

- AI 自维护记忆确保发言不矛盾，行为要符合逻辑以及自己身份的收益（"我之前说自己是民，现在除非特殊情况，不能无缘无故突然报查验"）
- 狼人 AI 不能直接暴露狼同伴
- 预言家 AI 不能报出未经查验的信息
- 女巫 AI 不能暴露药水状态（除非已决定跳身份）
- 后端不向客户端泄漏任何玩家的身份信息（除狼人互相可见）

### 5.2 系统架构（Command → Validate → Execute → Event → Reduce）

**核心设计原则**：
1. **AI 永远不能直接修改 GameState**——AI 只输出 Intent，经 Validator 校验后由引擎执行
2. **Command Bus** 统一入口——Socket、CLI、Test、Bot、Spectator 全部走同一 Command 层
3. **Reducer 纯函数**——`reduce(state, event) → { newState, effects[] }`，side effect 显式管理

```
┌──────────────────────────────────────────────────┐
│                    React 前端                      │

                     │

        ┌────────────┼────────────┬──────────────┐

   ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌──────────────┐
   │ Timer   │ │ Socket  │ │ TTS     │ │ AI Pipeline  │
   │ System  │ │ Broadcast│ │ Service │ │ (only reads  │
   │         │ │         │ │         │ │  GameState)  │
   └─────────┘ └─────────┘ └─────────┘ └──────┬───────┘

                          ┌────────────────────▼───────┐

                          │  "AI要投死人票→允许"       │

                          └────────────────────────────┘
```

**AI Pipeline 流程**：

```
GameState (只读)
    ↓
AI Pipeline: Think → Plan → Speak → Act
    ↓
AI Intent { type: "vote", target: "p3" }
    ↓
Intent Validator (合法性校验)
    ↓
Command Bus
    ↓
Engine Reducer → New State + Effects
```

> **关键约束**：AI Pipeline 只能读取 GameState，永远不能写入。AI 的"行动"是提交 Intent，和人类玩家走同一 Command Bus 路径。

### 5.3 游戏状态机（事件驱动 + 条件跳转）

**核心架构模式**：Functional Core / Imperative Shell。
- **Functional Core**：Reducer 是纯函数，`(state, event) → { state, effects[] }`，可测试、可回放
- **Imperative Shell**：Effect Runtime 执行所有副作用（Timer、AI、Socket、Persist）

#### 5.3.0 Projection 分层（玩家视图 vs 上帝视图）

`GameState` 是服务端完整状态（上帝视图）。客户端收到的必须经过 Projection 过滤：

```typescript
// 所有用户操作和AI输出都走这个函数
buildPlayerView(state: GameState, playerId: string): PlayerView

// PlayerView 只包含该玩家有权看到的信息：
// ✅ 公开发言、投票结果、死讯、存活状态
// ❌ 其他玩家的身份、狼同伴、查验结果（除非是该玩家自己的）
```

**三层事件**：
- **Domain Event**（内部）：`wolf:kill_selected` — 完整信息，仅引擎可见
- **System Event**（中转）：`wolf:action_submitted` — AI/人类操作记录
- **Client Event**（外部）：`night_result_revealed` — 脱敏后的客户端推送

传统线性状态机（A→B→C→D）无法覆盖狼人杀的复杂分支。采用**条件状态图**：每个状态完成后，由**转移函数**根据游戏上下文决定下一状态。

#### 5.3.1 核心原则

1. **状态即阶段**：每个状态 = 一个游戏阶段，拥有独立的 onEnter / onComplete / 超时处理
2. **转移由条件驱动**：`nextState = transition(currentState, gameContext)` 而非硬编码顺序
3. **中断可插入**：任何状态可被"自爆""猎人开枪"等事件中断，插入临时状态后恢复
4. **角色自注册**：新角色只需在配置中声明"需要哪些阶段"，状态机自动编排
5. **模板可组合**：不同游戏模板（6人/9人/12人）通过阶段声明组合，无需修改状态机代码
6. **Phase Driver 推进**：阶段切换由专用的 Phase Driver 管理（`isPhaseComplete()` → `completePhase()` → `determineNextPhase()`），不散落在 Reducer 的 if/else 中

#### 5.3.2 状态清单

```
【初始阶段】
GAME_INIT            → 分配身份，初始化状态

【夜晚阶段】（按角色声明顺序自动编排）
NIGHT_WEREWOLF       → 狼人协商刀人（两轮异步协商）
NIGHT_SEER           → 预言家查验身份
NIGHT_WITCH          → 女巫决定是否用药（解药/毒药）
NIGHT_GUARD          → 守卫选择守护目标（P2加入）

【白天阶段】
DAY_BREAK            → 公布死讯（或平安夜公告）
                     → 检查胜负条件 CHECK_WIN
COMMON_LAST_WORDS    → 遗言阶段（条件触发：首夜死者/首轮被票者/非最后轮被刀者）
HUNTER_SHOOT         → 猎人开枪（条件触发：猎人被票出 且 非被毒杀）
CHECK_WIN            → 胜负条件检测（每有人出局后触发）
SELF_EXPLODE         → 狼人自爆（中断触发：白天阶段任意时刻）

【发言阶段】
SHERIFF_ELECTION     → 警长竞选（条件触发：12人局首日）
DAY_DISCUSS          → 按顺序发言（可被自爆中断）

【投票阶段】
DAY_VOTE             → 暗投 + 同时开票（不可跟票）
TIE_BREAK_SPEECH     → 平票PK发言（条件触发：平票时）
TIE_BREAK_VOTE       → 平票PK投票
EXILE                → 放逐结果公告
                     → 触发：HUNTER_SHOOT（如被票者为猎人）→ COMMON_LAST_WORDS → CHECK_WIN

【终局】
GAME_OVER            → 公布结果，MVP/SVP评选
```

#### 5.3.3 条件转移逻辑（伪代码）

```typescript
class GameStateMachine {
  transition(current: Phase, ctx: GameContext): Phase {
    switch (current) {
      case NIGHT_WEREWOLF:
        return NIGHT_SEER  // 有预言家 → 执行，否则跳过

      case NIGHT_SEER:
        return ctx.roles.hasGuard ? NIGHT_GUARD : NIGHT_WITCH

      case NIGHT_WITCH:
        return DAY_BREAK

      case DAY_BREAK:
        if (ctx.isGameOver) return GAME_OVER
        // 检查是否有遗言触发
        if (ctx.needsLastWords) return COMMON_LAST_WORDS
        // 检查猎人是否被票出（从前一轮投票来）
        if (ctx.hunterKilledByVote && !ctx.hunterPoisoned) return HUNTER_SHOOT
        // 警长竞选
        if (ctx.isFirstDay && ctx.config.hasSheriff) return SHERIFF_ELECTION
        return DAY_DISCUSS

      case DAY_DISCUSS:
        // 可被 SELF_EXPLODE 中断
        return DAY_VOTE

      case DAY_VOTE:
        if (ctx.voteResult.isTie) return TIE_BREAK_SPEECH
        return EXILE

      case TIE_BREAK_SPEECH:
        return TIE_BREAK_VOTE

      case TIE_BREAK_VOTE:
        if (ctx.voteResult.isTie) return NIGHT_WEREWOLF  // 仍平票，无人出局
        return EXILE

      case EXILE:
        if (ctx.hunterKilledByVote && !ctx.hunterPoisoned) return HUNTER_SHOOT
        if (ctx.needsLastWords && ctx.exiledPlayerEligible) return COMMON_LAST_WORDS
        if (ctx.isGameOver) return GAME_OVER
        return NIGHT_WEREWOLF

      case COMMON_LAST_WORDS:
        if (ctx.isGameOver) return GAME_OVER
        if (ctx.fromNightDeath) return DAY_DISCUSS  // 遗言结束 → 白天发言
        return NIGHT_WEREWOLF  // 被票出遗言 → 天黑

      case HUNTER_SHOOT:
        if (ctx.isGameOver) return GAME_OVER
        return COMMON_LAST_WORDS  // 猎人开的枪可能产生新遗言

      case SELF_EXPLODE:
        // 立即进入天黑，跳过投票
        return NIGHT_WEREWOLF

      // ... 更多条件
    }
  }
}
```

#### 5.3.4 中断机制

某些事件可以在**任意白天阶段**被触发，插入临时状态：

```typescript
// 中断处理器
class InterruptHandler {
  // 狼人自爆：发言阶段任意时刻
  onSelfExplode(): Phase {
    // 保存当前状态（用于恢复）
    this.savedState = this.currentPhase
    // 公开狼人身份 → 直接进入天黑
    return SELF_EXPLODE
  }

  // 猎人开枪：在 EXILE 后被条件触发，而非中断
  // 不在投票阶段中间触发（避免混乱）
}
```

**自爆是唯一的中断型事件**。其余（遗言、猎人开枪、平票）都是条件跳转，在正常状态转移流程中判断。

#### 5.3.5 角色→阶段声明

每个角色通过声明"我需要在哪些阶段行动"来注册到状态机：

```typescript
// 角色定义中的阶段声明
const RolePhaseDeclarations = {
  werewolf: {
    nightActions: [NIGHT_WEREWOLF],      // 狼人需要在狼人夜行动
    dayAbilities: [SELF_EXPLODE],         // 可自爆（中断能力）
    triggersOnDeath: [],                   // 死亡不触发额外阶段
  },
  seer: {
    nightActions: [NIGHT_SEER],
  },
  witch: {
    nightActions: [NIGHT_WITCH],
  },
  guard: {
    nightActions: [NIGHT_GUARD],
  },
  hunter: {
    triggersOnDeath: [HUNTER_SHOOT],      // 死亡时可能触发开枪
    deathCondition: (ctx) => !ctx.poisonedByWitch, // 不能是被毒
  },
  villager: {
    // 无特殊阶段
  },
}
```

这样加一个新角色（如"白痴"），只需声明其阶段和行为，状态机自动编排。

#### 5.3.6 死亡原因追踪

状态机需要区分死亡原因，因为不同原因触发不同后续：

```typescript
enum DeathCause {
  WOLF_KILL,        // 被狼人刀
  VOTE_EXILE,       // 被投票放逐
  WITCH_POISON,     // 被女巫毒杀
  HUNTER_SHOT,      // 被猎人开枪
  GUARD_WITCH_SAME, // 同守同救
}

// 影响后续流程：
// - 被毒杀的猎人 → 不能开枪
// - 首夜被刀 → 触发遗言
// - 被票出的猎人 → 触发开枪
// - 同守同救 → 该玩家死亡，归属 GUARD_WITCH_SAME
// - 女巫毒杀 + 狼刀同时致死 → 死亡原因分别为 WITCH_POISON 和 WOLF_KILL，各自记录，不合并
// - 猎人开枪 + 女巫毒杀同一人 → 先执行的开枪，毒杀被跳过（目标已死亡）
```

#### 死亡原因唯一性

一轮中一个玩家可能有多个死亡来源（如同时被刀和被毒）。处理原则：
- 每个死亡原因生成独立的 `player:died` 事件
- `deathInfo.cause` 存储**实际致死原因**（按操作顺序：狼刀→女巫毒→女巫救→守卫守→结算）
- 若已被救活/守护，则不生成死亡事件
- 遗言资格由"是否首夜/首票"和"是否最后一轮"决定，与死亡原因无关（除同守同救无遗言）
```

### 5.5 发言流水线时间模型 & 超时配置

#### 各阶段超时时间表

| 阶段 | 真人操作时限 | AI 执行时间 | 超时处理 |
|------|-------------|------------|----------|
| 狼人夜（第1轮协商） | 15s | ~5s | 超时 → 随机刀人 |
| 狼人夜（第2轮协商） | — | ~5s | 超时 → 多数决 |
| 预言家夜 | 10s | ~5s | 超时 → 随机查验 |
| 女巫夜 | 15s | ~5s | 超时 → 不使用药 |
| 守卫夜（Phase 3） | 10s | ~5s | 超时 → 不守护 |
| 白天发言（文字输入） | **180s** | — | 超时 → 自动过麦 |
| 白天发言（语音输入） | 180s（含录音+STT） | — | 同上 |
| AI 发言生成 | — | **≤ 60s** | 超时 → 预置兜底发言 |
| 投票 | 15s | ~5s | 超时 → 弃票 |
| 遗言 | 60s | ~10s | 超时 → 跳过 |
| 猎人开枪 | 15s | ~5s | 超时 → 不开枪 |
| 狼人自爆 | 5s（确认操作） | — | — |
| 平票PK发言 | 60s | ~10s | 超时 → 跳过 |

> 时间设计原则：AI 的短、人的长。AI 生成发言放宽到 60s 以内保证质量，后续可收紧。

#### 发言流水线（修正）

```
白天发言阶段 — 以10人局为例：

【预思考阶段】(所有存活AI并发)
  ├─ 所有AI基于当前信息构建初始发言框架
  └─ 耗时：~10s（并行）

【正式发言阶段】(串行生成 + 并行思考)
  ├─ 发言1生成(10-30s)
  │   ├─ [所有其他AI立即读取文本 → 更新内部判断]   < 1s
  │   └─ [TTS播放给人类]                          15-30s
  ├─ 发言2生成(10-30s)
  │   ├─ [所有其他AI立即读取文本 → 更新内部判断]
  │   └─ [TTS播放]
  ├─ ...
  └─ 发言10生成(10-30s)
      ├─ [所有其他AI立即读取文本 → 更新内部判断]
      └─ [TTS播放]

AI总处理时间：~100-300s（上限 60s/人 × 10人 = 600s 硬顶）
人类感知时间（TTS播放）：~2.5-5min（AI生成+思考完全淹没在TTS窗口中）
```

> AI 处理时间完全淹没在 TTS 播放窗口内，不会造成额外等待。真人 180s 输入时间 + AI 60s 生成时间保证了发言深度。

### 5.6 可视化工作流编辑器（P2）

#### 5.6.1 设计目标

#### 5.6.2 编辑器界面

### 5.8 事件溯源（Event Sourcing）

狼人杀本质是**时序推理游戏**——AI 的推理依赖"谁在什么时候做了什么"。事件日志是系统的核心数据源，Debug、回放、AI 记忆、观战全都依赖它。

#### 设计原则

```
GameState = reduce(allEvents)     // 状态由事件累积计算，而非直接修改
```

不直接修改 mutable state，而是追加事件，状态由事件重放得出。

#### 事件类型清单

```typescript
type GameEvent =
  // 房间事件
  | { type: "room:created"; roomCode: string; config: GameConfig; ts: number }
  | { type: "player:joined"; playerId: string; name: string; seat: number; ts: number }
  | { type: "player:left"; playerId: string; seat: number; ts: number }
  | { type: "game:started"; ts: number }

  // 身份事件（私有事件，仅目标玩家可见）
  | { type: "role:assigned"; playerId: string; role: Role; ts: number; visibleTo: string[] }
  | { type: "wolf:teammates"; playerId: string; teammates: string[]; ts: number; visibleTo: string[] }

  // 夜晚事件
  | { type: "night:phase_started"; round: number; ts: number }
  | { type: "wolf:action_submitted"; playerId: string; target: string; reason: string; ts: number; visibleTo: string[] }
  | { type: "wolf:action_resolved"; targets: string[]; ts: number }
  | { type: "seer:action_submitted"; playerId: string; target: string; ts: number; visibleTo: string[] }
  | { type: "seer:result"; playerId: string; target: string; result: "good" | "wolf"; ts: number; visibleTo: string[] }
  | { type: "witch:action_submitted"; playerId: string; saveTarget?: string; poisonTarget?: string; ts: number; visibleTo: string[] }
  | { type: "witch:result"; savedPlayer?: string; poisonedPlayer?: string; ts: number }

  // 白天事件
  | { type: "day:break"; round: number; deaths: DeathAnnouncement[]; isSafeNight: boolean; ts: number }
  | { type: "self_explode:triggered"; playerId: string; ts: number }
  | { type: "speech:turn_started"; playerId: string; seat: number; timeLimit: number; ts: number }
  | { type: "speech:submitted"; playerId: string; content: string; ts: number }
  | { type: "last_words:submitted"; playerId: string; content: string; ts: number }
  | { type: "vote:cast"; playerId: string; target: string | null; ts: number; visibleTo: [] }  // 暗投期间不可见
  | { type: "vote:revealed"; votes: { player: string; target: string | null }[]; ts: number }
  | { type: "vote:tie_break_speech"; players: string[]; ts: number }
  | { type: "player:exiled"; playerId: string; voteCount: number; ts: number }
  | { type: "hunter:shot"; playerId: string; target: string; ts: number }

  // 终局
  | { type: "player:died"; playerId: string; cause: DeathCause; killerId?: string; ts: number }
  | { type: "game:ended"; winner: Faction; mvp: string; svp: string; ts: number }
```

#### 事件可见性

- **公开事件**：所有玩家可见（发言、投票结果、死讯）
- **私有事件**：仅特定玩家可见（身份、同伴、查验结果、狼人提案）
- **临时隐藏**：暗投期间投票事件的 `visibleTo: []`，开票后改为公开

#### 事件存储

- 每局游戏的事件流以 JSON Lines 格式存储
- `game_events/{gameId}.jsonl`
- 回放 = 按序重放事件流
- 断线重连 = 从断线时间点开始补发事件
- 所有事件带 `version` 字段，向后兼容

#### 事件分类体系

事件按用途分为五层，避免单一事件被多种消费者耦合：

| 分类 | 用途 | 消费者 | 示例 |
|------|------|--------|------|
| **Domain Events** | 游戏规则事件 | Reducer, Replay, AI Memory | `player:died`, `vote:revealed` |
| **System Events** | 超时/断线/恢复 | Engine, Timer System | `phase:timeout`, `player:reconnected` |
| **AI Events** | Prompt/LLM调用 | AI Pipeline, Debugger | `ai:prompt_sent`, `ai:response_received` |
| **UI Events** | 动画/提示 | Frontend | `animation:night_start`, `toast:vote_reminder` |
| **Audit Events** | Debug/Replay/分析 | LLM Judge, Admin Panel | `state:snapshot`, `intent:rejected` |

> AI Memory 只订阅 Domain Events，前端只订阅 Domain + UI Events，互不污染。

#### 事件版本化 & 迁移

所有 Event 类型带 `version` 字段。当协议升级时：

```
event_v1 → migration function → event_v2
```

回放系统自动检测事件的 `version`，按顺序应用 migration function 升级到最新版本后再重放。确保旧对局日志永远可回放。

#### 事件幂等性

多人同步/断线重连时可能出现重复事件。所有 Event 携带幂等字段：

```typescript
{
  eventId: string          // 唯一事件 ID（UUID v7）
  causationId: string      // 触发该事件的 Command ID
  correlationId: string    // 同一操作链的事件共享此 ID
  idempotencyKey: string   // 幂等键（相同 key 的事件 Reducer 只处理一次）
}
```

Reducer 通过 `idempotencyKey` 去重，防止断线重连/重试导致状态错误。

### 5.9 阶段 → 子阶段细化

当前状态机按 Phase 划分，但狼人杀真正复杂的是每个 Phase 内部的 SubPhase 切换（动画、倒计时、AI Thinking、TTS 都依赖细粒度状态）。

#### 子阶段定义

```
NIGHT
 ├─ NIGHT_ANNOUNCE          → "天黑请闭眼"
 ├─ WOLF_INTEL              → 狼人互相确认（推送同伴信息，不走 LLM）
 ├─ WOLF_PROPOSE            → 狼人第1轮提案（并发 LLM）
 ├─ WOLF_RESOLVE            → 狼人第2轮决议（如需）
 ├─ SEER_CHOOSE             → 预言家选择查验目标
 ├─ SEER_RESULT             → 引擎返回查验结果（不走 LLM）
 ├─ WITCH_NOTIFY            → 引擎推送死者信息（不走 LLM）
 ├─ WITCH_DECIDE            → 女巫决策是否用药
 ├─ GUARD_CHOOSE            → 守卫选择守护目标（Phase 3）
 └─ NIGHT_SETTLEMENT        → 结算夜晚结果

DAY
 ├─ DAY_BREAK               → 天亮公告
 ├─ DEATH_ANNOUNCE          → 公布死讯 / 平安夜
 ├─ CHECK_WIN               → 胜负检测
 ├─ COMMON_LAST_WORDS       → 遗言（条件触发）
 ├─ HUNTER_SHOOT            → 猎人开枪（条件触发）
 ├─ SHERIFF_ELECTION        → 警长竞选（条件触发）
 ├─ SPEECH_PRE_THINK        → AI 预思考（并发，不阻塞 UI）
 ├─ SPEECH_TURN_ACTIVE      → 当前玩家发言中（倒计时）
 ├─ SPEECH_TURN_DONE        → 发言完成，短暂停顿
 ├─ VOTE_CAST               → 暗投中（投票不可见）
 ├─ VOTE_REVEAL             → 统一开票
 ├─ TIE_BREAK_SPEECH        → 平票 PK 发言
 ├─ TIE_BREAK_VOTE          → 平票 PK 投票
 ├─ EXILE_ANNOUNCE          → 放逐公告
 └─ DAY_SETTLEMENT          → 白天结算

GAME_OVER
 ├─ RESULT_ANNOUNCE         → 公布胜负
 └─ MVP_ANNOUNCE            → MVP/SVP 公布
```

每个 SubPhase 有独立的：
- 超时时间
- 客户端 UI 状态（显示什么、隐藏什么）
- TTS / 音效触发

### 5.10 AI Pipeline 结构化分层

**MVP 降级策略**：为防止成本和延迟爆炸，Phase 1 不做显式 Think/Plan 层。

```
MVP (v0.1):  Context → Speak/Act（Think/Plan 隐式在 LLM 内完成）
v0.2:        Context → Think → Speak/Act
v1.0:        Context → Think → Plan → Speak → Act
```

MVP 只做一层 LLM 调用——发言和行动在一次流式调用中完成。后续版本逐步拆细推理层。详细分层 Schema 见下方（全四层设计，以备 v1.0 启用）。

AI 决策不是"一次性生成全部"，而是分层进行。每一层有明确的输入输出格式，便于稳定、Debug、切换模型。

```
┌──────────────┐
│  Think       │  内部推理层（私有，不对外暴露）
│  输出: 信念更新、怀疑度、策略评估
├──────────────┤
│  Plan        │  策略规划层（私有）
│  输出: 本轮发言策略、投票倾向、伪装方向
├──────────────┤
│  Speak       │  公开发言层
│  输出: 自然语言发言文本
├──────────────┤
│  Act         │  最终行动层
│  输出: 结构化操作（投票目标 / 刀人目标 / 查验目标）
└──────────────┘
```

#### 各层 Schema

```typescript
// Think 层输出
interface AIThought {
  beliefs: Record<string, { role: string; confidence: number }>  // 对各玩家身份的信念
  suspicion: Record<string, { level: number; reason: string }>    // 怀疑度
  threatAssessment: string                                         // 当前威胁评估
  strategyEvaluation: string                                       // 当前策略是否仍然有效
}

// Plan 层输出
interface AIPlan {
  speechStrategy: string       // 本轮发言策略（如"引导怀疑3号"）
  voteIntention: string | null // 当前投票倾向
  fakeRole: string             // 当前伪装身份
  keyPoints: string[]          // 发言要点列表
}

// Speak 层输出
interface AISpeech {
  content: string              // 150-400 字发言
  tone: string                 // 语气标签（激进/温和/困惑等）
}

// Act 层输出
interface AIAction {
  type: "vote" | "wolf_kill" | "seer_check" | "witch_save" | "witch_poison" | "guard" | "self_explode" | "hunter_shoot" | "skip"
  target: string | null
  reason: string
}
```

> 分层调用而非一次生成——各层失败可独立重试，低层（Think）失败不影响高层（Speak）的兜底输出。

#### Prompt Contract & 文件组织

必须严格 Schema 化 Prompt 的输入输出，防止 Prompt 改动 silently break Parser。

```typescript
// Contract
buildPrompt(context: AIContext) → PromptInput    // 输入必须符合 Schema
parseResponse(raw: string) → AIIntent            // 输出必须可解析
```

每局保存**完整 prompt snapshot**（不只是 version），包含：
- system prompt 全文
- 角色 policy 全文
- few-shot examples 全文
- 参数（temperature, top_p, max_tokens）

**原因**：只存 version 字符串无法复现——v3 prompt 的 few-shot/system/role 内容可能已变，Replay 失真。

#### Prompt 文件组织

```
/aiwolf/prompts/          ← 项目根目录，独立于代码
  /system/                ← 系统 Prompt
  /roles/                 ← 角色 Prompt（werewolf/seer/witch/villager）
  /phases/                ← 阶段 Prompt（night/day/vote/last_words）
  /fewshots/              ← Few-shot examples
  /judge/                 ← 裁判 Prompt
```

Prompt 与代码分离：代码只负责 `loadPrompt(path)` + 变量替换。Prompt 修改不走代码部署，支持热更新。

### 5.11 Token Budget 管理

狼人杀发言历史增长极快（10 人局 3 轮发言 ≈ 6000 字文本），不加控制会在第 3 轮爆上下文窗口。

#### Context Builder 分层注入

```
┌──────────────────────────────────┐
│ System Prompt           ~500 tok │  固定，不随轮次增长
├──────────────────────────────────┤
│ Persona                 ~200 tok │  固定
├──────────────────────────────────┤
│ Role Knowledge          ~800 tok │  固定（策略知识库 v1）
├──────────────────────────────────┤
│ Hidden Info            ~200 tok  │  固定（身份+同伴+药水）
├──────────────────────────────────┤
│ Long-term Memory       ~500 tok  │  AI 自维护摘要，每轮更新
├──────────────────────────────────┤
│ Current Round Summary  ~400 tok  │  本轮关键事件摘要（由 Summarizer 生成）
├──────────────────────────────────┤
│ Recent Speeches       ~2000 tok  │  最近 5 条发言原文
├──────────────────────────────────┤
│ Current Task           ~300 tok  │  当前要做什么
├──────────────────────────────────┤
│                        ~4900 tok │  总计（可控）
└──────────────────────────────────┘
```

#### 历史摘要器（Summarizer）

```
完整发言历史(可能 15000 tok)
       ↓
Summarizer 压缩（调用轻量 LLM 或规则引擎）
       ↓
结构化摘要：
  "第1天：2号跳预言家报5号金水。3号强踩5号。投票结果：5号被票出，身份村民。
   第2天：1号被杀。4号被怀疑..."
       ↓
注入 Current Round Summary (~400 tok)
```

**摘要由轻量模型生成**（如 GPT-3.5-turbo），不占用主力模型的 token。

#### Token 预算上限

| 组件 | 上限 | 说明 |
|------|------|------|
| System + Persona + Knowledge | 1500 tok | 固定 |
| Memory + Summary | 1000 tok | AI 自维护，每轮更新 |
| Recent Speeches | 3000 tok | 最近 5-8 条发言原文 |
| Current Task | 500 tok | 可变 |
| **总计** | **≤ 6000 tok** | 远低于常见 128k 窗口，留足推理空间 |

> 当 Recent Speeches 超过上限时，最旧的发言被 Summarizer 压缩后移入 Memory。

#### AI 预算控制

狼人杀每局易产生 100-300 次 LLM 调用。不加预算控制成本会爆炸。

```typescript
interface AIBudget {
  maxPromptTokens: number       // 单次 Prompt 上限（默认 6000）
  maxCompletionTokens: number   // 单次响应上限
  maxCallsPerPhase: number      // 每阶段最大调用次数
  maxTotalCallsPerGame: number  // 每局总上限
  currentCalls: number          // 当前计数
}
```

**分层模型策略**：
- **关键发言/投票**：主力模型（GPT-4o / Claude Sonnet）
- **策略复核/记忆更新**：轻量模型（GPT-3.5-turbo）
- **Summarizer**：最轻量模型（GPT-3.5-turbo mini）

> 在 AIConfig 中可配置每个 AI 任务的模型选择，成本预估：主力模型 ~$0.15/局、轻量 ~$0.03/局。

#### 上下文压缩策略

| 层级 | 保留策略 | 实现 |
|------|----------|------|
| 最近 5-8 条发言 | **全量保留原文** | 直接注入 |
| 早期发言 | **结构化摘要** | Summarizer 压缩为"第X天，X号说了Y，结论是Z" |
| 往轮推理 | **内容摘要** | "第1天我判断1号像民，第2天开始怀疑2号" |
| 长期记忆 | **标签化** | 关键事件打标签（"自刀事件""悍跳对抗"），按需检索 |
| 系统状态 | **结构化数据** | 存活名单、药水状态等不占用 context token |

> Think 层输出（内部推理）和 Speak 层输出（公开发言）**分开存储**。Think 内容仅用于 AI 自身的 Memory 更新和 Debug 追溯，不进入后续 context。

### 5.12 时间系统

狼人杀是**强时间驱动系统**。多个 timer 并发、reconnect 打断、replay 一致性，都需要统一的时间模型。

#### 时间类型

| 类型 | 说明 | 示例 | 超时处理 |
|------|------|------|----------|
| **Hard Timeout** | 硬截止，到时强制执行 | 投票截止 | 超时 = 弃票 |
| **Soft Timeout** | 警告但不强制执行 | AI 思考超时 | 超时 = 切换到备用模型 |
| **Grace Period** | 宽限期 | 断线等待 | 240s 内可重连 |
| **Animation Delay** | 纯前端动画 | 天黑过渡 | 不影响状态机，仅延迟 UI |
| **Scheduled Event** | 定时触发 | "请在 10s 内决定用药" | 超时 = 不操作 |
| **Phase Cooldown** | 阶段间最小间隔 | 发言之间停顿 2s | 防止连续操作混乱 |

#### Timer 管理原则

- **Server 是唯一时间源**：客户端不决定 timeout、不决定 phase 切换、不决定 timer。客户端只显示服务端推送的剩余时间
- 所有 timer 由引擎管理，不由前端控制（前端只显示倒计时）
- 每个 Phase 进入时注册 timer，离开时销毁
- 断线重连不重置已过 timer（基于服务端真实时间计算剩余）
- Replay 模式下所有 timer 加速（跳过等待，直接快进）

#### 超时必须事件化

所有超时不通过 `setTimeout` 直接修改状态，而是生成 Timer Event 进入 Reducer：

```typescript
// ❌ 错误：直接改状态
setTimeout(() => { state.phase = nextPhase }, 30000)

// ✅ 正确：Timer 是 Effect，超时产生 Event
Effect: { type: "timer:start", phase: "vote", duration: 15000 }
→ 超时 →
Event: { type: "timer:expired", phase: "vote", playerId: "p3" }
→ Reducer: (state, event) → { state: { phase: "exile", ... }, effects: [] }
```

这样 Replay 时只需重放 Timer Event，不依赖真实时间流逝。

### 5.13 AI Fail Policy

LLM 是不可靠的。必须对每一种失败模式定义明确的降级策略。

| 失败场景 | 检测方式 | Phase 1 策略 |
|----------|----------|-------------|
| LLM API 超时 | 请求超过 60s 未响应 | ① 切换备用模型重试 ② 备用也超时 → Rule-based 兜底 |
| JSON 解析失败 | Response Parser 报错 | ① 重试 + 要求 LLM 修正格式 ② 仍失败 → 提取纯文本内容作为发言 |
| AI 输出非法行为 | Intent Validator 拒绝 | 日志记录 + 降级为"弃票/不操作" |
| AI 发言为空 | content.length < 10 | 使用预置兜底发言模板 |
| AI 连续失败 3 次 | 计数器 | 该 AI 进入"托管模式"：全部操作用 Rule-based 接管，每轮尝试恢复 |
| API Rate Limit | HTTP 429 | 自动退避 + 队列化请求 |
| Provider 完全不可用 | 所有模型失败 | 该局标记为"降级模式"，全 AI 切换 Rule-based，前端提示玩家 |

#### Rule-based AI（降级兜底）

```
狼人：随机选择活着的非狼人目标
预言家：随机选择未查验的存活玩家
女巫：首夜必救，之后不救；毒药随机使用
村民/猎人/守卫：随机弃票或跟票
```

**Rule-based AI 永不失败**，是系统的最终安全网。

### 5.15 Headless Engine 原则

游戏引擎必须是无头（Headless）的——不依赖 Socket、不依赖 React、不依赖 DB。

```
/packages/engine          ← 纯逻辑，零外部依赖
/packages/server          ← Express/Fastify + Socket.IO
/packages/client          ← React 前端
/packages/shared          ← 共享类型（Event, Intent, State Schema）
```

**引擎可独立运行**：

```bash
# 无头模拟
node packages/engine/cli.js simulate --template=6_player --rounds=100

# 无头回放
node packages/engine/cli.js replay --game-id=abc123
```

**原则**：
- Engine 包的测试不启动任何服务器
- Engine 包的输入输出都是纯数据（State + Event + Intent）
- 任何依赖 I/O 的逻辑都是 Effect，在 Effect Handler 中实现

#### 完整包结构

```
/packages
  /shared       ← 共享类型（Event/Intent/State/Zod Schema）
  /protocol     ← 协议定义（Event/Command/Socket Payload，独立于此）
  /engine       ← 纯逻辑，零外部依赖（除 shared/protocol）
  /ai           ← AI Pipeline（依赖 engine）
  /server       ← Express/Fastify + Socket.IO（依赖 engine+ai）
  /web          ← React 前端（仅依赖 shared 的 Payload 类型）
  /cli          ← CLI 工具（依赖 engine）
  /devtools     ← Event Viewer / State Inspector / Replay Runner / Prompt Viewer
```

> `protocol` 独立为包，因为 Event/Command/Socket Payload 是"跨边界语言"，不应散落在业务逻辑中。

### 5.16 Effect Runtime

Reducer 输出的 `effects[]` 数组需要统一调度执行，不能散落各处。

#### Effect 类型

```typescript
type Effect =
  | { type: "timer:start"; phase: PhaseType; duration: number; onTimeout: PhaseType }
  | { type: "timer:cancel"; phase: PhaseType }
  | { type: "ai:request"; playerId: string; task: AITask; context: AIContext }
  | { type: "socket:broadcast"; roomId: string; event: string; payload: unknown }
  | { type: "socket:whisper"; playerId: string; event: string; payload: unknown }
  | { type: "tts:speak"; text: string; playerId: string }
  | { type: "persist:event"; event: GameEvent }
  | { type: "persist:snapshot"; state: GameState }
  | { type: "log:audit"; level: "info"|"warn"|"error"; message: string }
```

#### Effect Scheduler

```typescript
// Reducer 返回 effects，不执行
const { newState, effects } = reduce(currentState, event)

// Effect Scheduler 统一执行所有 effect
await effectScheduler.run(effects, context)
```

**执行顺序**：先 Timer（确保超时注册），再 AI（异步非阻塞），再 Broadcast（通知客户端），最后 Persist。

**执行模型**：
- **队列化执行**：同类型 Effect 按产生顺序执行（如多个 Broadcast 依次推送）
- **优先级**：Timer > AI > Broadcast > Persist。Timer 永远最先，确保超时保护生效
- **取消策略**：Phase 切换时取消所有旧 Phase 的 Timer 和未完成的 AI 请求
- **错误隔离**：单个 Effect 失败不影响其他 Effect 执行（如 TTS 挂了不影响 Broadcast）
- **并发控制**：AI 请求可并发（不同玩家），但同一玩家的 Think→Plan→Speak→Act 严格串行

### 5.17 Snapshot 策略

纯 Event Sourcing 在事件数 ≥ 3000 时回放会变慢。采用定期 Snapshot 加速。

#### Snapshot Policy

```
每 50 个 Domain Event 生成一次 State Snapshot

Snapshot 结构：
{
  lastEventId: string
  state: GameState
  checksum: string          // SHA256 校验和，防篡改
}

Replay 流程：
  1. 找到最近的 Snapshot → 加载 State
  2. 从 Snapshot 之后的事件开始重放
  3. 只执行 Reducer，跳过 Effect（回放不需要 Timer/AI/Socket）
```

#### 数据持久化

| 数据 | 持久化 | 原因 |
|------|--------|------|
| Event Stream | ✅ | 不可重建，唯一真相源 |
| State Snapshot | ✅ | 加速回放，可从 Event 重建 |
| Prompt Trace | ✅ | Debug AI 行为必需 |
| AI Raw Response | ✅ | 回溯 AI 原始输出 |
| Reducer Derived State | ❌ | 可从 Event Stream 重建 |

## 7. 非功能性需求

### 7.1 性能

- AI 发言生成延迟 < 8 秒（含前置发言分析）
- AI 夜晚决策延迟 < 5 秒（含狼人两轮协商）
- WebSocket 消息延迟 < 200ms
- 首屏加载 < 3 秒

### 7.2 体验

- AI 发言无逻辑矛盾（自维护记忆保证一致性）
- AI 发言风格区分度明显（不同 persona）
- AI 策略有变化和对抗（不是每局一样）
- 夜晚操作有倒计时提示
- AI 思考/生成中前端有过渡动画（打字效果 / "思考中..."）

### 7.3 安全性

- 房间号足够随机，不易被猜测进入
- 客户端不可获取其他玩家的身份信息（除狼人同伴外）
- 狼人同伴信息仅在 AI 内部记忆和夜晚协商中使用，不传输到客户端

### 7.4 测试策略

| 测试类型 | 覆盖内容 | 方法 | Phase |
|----------|----------|------|-------|
| 状态机单元测试 | 每个条件转移路径 + 中断机制 + 死亡原因分支 | Jest / Vitest 单元测试，Mock 游戏上下文，断言 `transition()` 返回值 | P0 |
| LLM 裁判自动评审 | AI 发言连贯性、逻辑合法性、一致性 | 高阶 LLM（GPT-4o / Claude Sonnet）读取对局日志，按评分 rubric 打分，生成评审报告 | P1 |
| AI 一致性回归测试 | AI 不自相矛盾（如声称自己是民后又报查验） | 20 局 AI vs AI → LLM 裁判评分 → 低于阈值则报警 | P1 |
| 游戏引擎集成测试 | 完整 6 人局从开始到结束 | 6 AI 自动对战，断言胜负判定正确、角色技能正确触发 | P0 |
| 多人联机测试 | 2+ 真人同时在线 | 真实浏览器测试，验证房间/同步/断线重连+数据补发 | P1 |
| AI 策略有效性 | AI 是否合理使用策略、是否适时切换 | 运行 20 局，LLM 裁判按策略维度评分（策略选择合理性、切换时机等） | P1 |
| 压力测试 | 10 局并发、LLM API 延迟峰值 | 自动脚本 + API mock | P2 |
| **蒙特卡洛模拟** | 状态机是否卡死/非法状态/无穷循环 | **1000 局 Rule-based AI** 自动对战，检查：卡死率 = 0%、非法状态 = 0%、阵营胜率不异常 | P0 |
| **不变量测试** | 任意事件序列是否违反基本约束 | Property-based Testing（fast-check）：随机事件序列 → 断言"dead player 不能发言""不能重复投票""不能 phase 跳跃" | P0 |
| **局后一致性检查** | 游戏结束后的逻辑一致性 | 自动化断言：① 死亡人数 + 存活人数 = 总人数；② 胜利方符合规则（不能双赢）；③ 狼人不可能票狼人出局（除自爆）；④ 女巫药水使用次数 ≤ 1；⑤ 没有玩家被重复杀死 | P0 |

> 蒙特卡洛模拟在每次代码变更后自动运行，是比人工测试更可靠的回归护栏。

#### LLM 裁判设计

```
输入：一局完整对局日志（发言历史 + 投票记录 + 身份信息）
Prompt：
  "你是狼人杀裁判。请对以下对局中的 AI 玩家进行评分：
  
  评分维度（每项 1-10 分）：
  1. 发言连贯性：前后发言是否自洽，没有自相矛盾
  2. 逻辑合法性：推理是否合理，是否基于已知信息
  3. 策略执行：是否遵循角色策略，策略切换是否合理
  4. 身份隐藏：是否适当隐藏真实身份（狼人/神职）
  5. 自然度：发言是否像人类，没有 AI 味
  
  请提供每个玩家的评分 + 扣分理由 + 典型案例引用。"

输出：结构化评分 JSON + 评审摘要
```

**自动化流程**：
```
跑 N 局 AI vs AI → 日志落盘 → LLM 裁判批量评审 → 生成评分报告
  ↓
任一维度均分 < 6 分 → 标记为回归 → 人工复查
全部维度均分 ≥ 7 分 → 通过
```

**裁判可靠性验证**：Phase 2 搭建 10 局人类评审 vs AI 评审的基准数据，计算 Pearson 相关系数。若相关性 < 0.7，调整裁判 prompt 直至达标。否则 7 分门槛可能无意义。

**Phase 1 验收方式**：状态机单元测试全绿 + 1000 局蒙特卡洛通过 + 20 局 LLM 裁判通过（均分 ≥ 7）。

#### AI 行为评估维度

| 维度 | 指标 | 目标 |
|------|------|------|
| 逻辑一致性 | 是否自相矛盾 | 零矛盾 |
| 身份隐蔽性 | 狼人/神职是否过早暴露 | 狼人平均存活 ≥ 3 轮 |
| 发言多样性 | 是否模板化/重复 | 连续两局相同策略的发言相似度 < 0.5 |
| 社交真实感 | 是否像真人 | LLM 裁判"自然度" ≥ 7 |
| 推理深度 | 是否只会复读/划水 | 发言含推理链比例 ≥ 80% |
| 游戏推进能力 | 是否导致卡场 | 人均发言 ≥ 100 字，零"跳过" |

> 这些维度指导 AI 调优方向，防止"优化了逻辑但体验变差"。

### 7.5 可观测性

AI + 状态机复杂度高，没有可观测性 Debug 会地狱。

| 工具 | 用途 | Phase |
|------|------|-------|
| **Event Log Viewer** | 可视化事件时间线，逐条查看每局事件 | P1 |
| **State Snapshot Diff** | 查看某事件前后的 State 变化 | P1 |
| **AI Prompt Trace** | 记录每次 LLM 调用的 prompt → response → parsed result | P0 |
| **Prompt Trace 元数据** | 每次 LLM 调用记录：model, temperature, top_p, latency_ms, input_tokens, output_tokens, parse_duration_ms | P0 |
| **Replay Inspector** | 回放模式下暂停/快进/单步查看 AI 的 Think/Plan/Speak/Act | P1 |
| **AI Fail Dashboard** | 统计 AI 失败率、降级次数、Rule-based 接管次数 | P1 |
| **Game Health Metrics** | 每局卡死率、平均轮次、阵营胜率分布 | P2 |

**Phase 1 最低要求**：AI Prompt Trace 必须可用——每局游戏记录完整的 prompt/response 日志。没有这个，AI 行为 Debug 完全不可行。
